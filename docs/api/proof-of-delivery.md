# Proof of delivery — ZD-24 / #59

S3 Dispatch & Courier owns assignments and proof. S2 Parcel & Pricing remains the only
parcel-status writer. This implementation's evidence fields are **proposed and await
issue owner/reviewer approval**. No uploads, signatures, location or file storage are included.

## Authentication and ownership

All endpoints require a valid `COURIER` JWT, verified by the existing security starter.
Use the existing gateway `/api/v1/courier/**` route. S3 resolves the caller using S1
`GET /api/v1/users/courier-profile` with the courier bearer token. Both returned canonical
profile ID and app-user ID must match the local assignment. JWT `sub` is a distinct identity;
it is stored as the submitting actor, never compared to either UUID. Effective eligibility
requires `active=true` and `accountStatus=ACTIVE`. Identity failures fail closed.

No dispatcher override exists. Every proof read checks ownership before fetching evidence.
Responses use `Cache-Control: no-store`. Lists contain no evidence. There are no public
proof endpoints and no evidence is included in status requests or Kafka events.

## Endpoints

| Method | Path | Response |
|---|---|---|
| GET | `/api/v1/courier/deliveries` | Array of own delivery summaries |
| GET | `/api/v1/courier/deliveries/{parcelId}` | Own delivery summary |
| POST | `/api/v1/courier/deliveries/{parcelId}/proof` | 201 first submission, 200 identical replay |
| GET | `/api/v1/courier/deliveries/{parcelId}/proof` | 200 protected evidence and completion state |

`parcelId` is the existing assignment primary key, a UUID. There is no separate delivery ID.
The list includes all assignments, not a date-filtered or parcel-status-filtered subset.
Delivery summary:

```json
{
  "parcelId": "11111111-1111-4111-8111-111111111111",
  "courierId": "22222222-2222-4222-8222-222222222222",
  "assignedAt": "2026-11-04T10:00:00Z",
  "proofId": null,
  "completionState": null
}
```

The API does not invent tracking references, recipient addresses or parcel status.

POST body:

```json
{
  "recipientName": "Nimal Perera",
  "notes": "Received by customer",
  "proofReference": "POD-2026-001"
}
```

| Field | Validation after trimming |
|---|---|
| `recipientName` | Required, nonblank, maximum 100 Unicode characters |
| `notes` | Optional, blank becomes null, maximum 500 Unicode characters |
| `proofReference` | Required, nonblank, maximum 200 Unicode characters |

Java and the UI count Unicode code points to match PostgreSQL character limits.
The database enforces maximum lengths and nonblank required values as defense in depth.
Leading/trailing whitespace is normalized before persistence and replay comparison.
Normalization matches browser `String.trim()`, including nonbreaking spaces and BOM.
NUL characters are rejected with field validation errors before reaching PostgreSQL.

Proof response:

```json
{
  "proofId": "33333333-3333-4333-8333-333333333333",
  "parcelId": "11111111-1111-4111-8111-111111111111",
  "recipientName": "Nimal Perera",
  "notes": "Received by customer",
  "proofReference": "POD-2026-001",
  "submittedAt": "2026-11-04T11:00:00Z",
  "completionState": "PENDING",
  "completedAt": null
}
```

`submittedAt` is generated by PostgreSQL. `completedAt` is S3 acknowledgment time, not
the S2 status-history timestamp. Actor subject is not exposed in the response.

## Persistence and idempotency

Migration `V2__proof_of_delivery.sql` creates `dispatch.proof_of_delivery`, with a unique
parcel association and a local FK to `dispatch.delivery_assignment`. No S1/S2 schema is changed.
Concurrent inserts use `ON CONFLICT DO NOTHING`; one proof wins. Identical normalized evidence
returns the same ID/timestamp. Different evidence returns 409. Evidence/actor/association/time
are immutable, enforced by a database trigger, while completion bookkeeping may change.

## Completion and recovery

Submission commits evidence with `PENDING`; the scheduled worker initiates completion on its
next poll. HTTP never runs inside an S3 database transaction.

| State | Meaning |
|---|---|
| PENDING | Stored; S2 confirmation outstanding or transient failure awaiting retry |
| COMPLETED | S2 returned matching parcel ID, `DELIVERED` status and a Boolean `changed` |
| REJECTED | S2 returned 409; transition rejected; evidence retained |
| BLOCKED | Missing/invalid service configuration, permanent dependency rejection, invalid success body or retry exhaustion |

S3 calls S2 directly: `PATCH /api/v1/parcels/{parcelId}/status` with only
`{"status":"DELIVERED"}` and a confidential client-credentials `SERVICE` token.
The courier token is never forwarded to S2. S2 `changed:false` is successful acknowledgment
of an already-delivered parcel. This supports retries after S2 committed but S3 lost the response.
It also permits late proof for an already-delivered parcel: the existing contract cannot prove
that this POD caused that transition. A stricter late-proof policy needs an approved S2 extension.

The worker claims at most ten rows per round, using `FOR UPDATE SKIP LOCKED` and an atomic
60-second lease. A unique lease token fences stale acknowledgments. Restarted workers reclaim
expired leases. Attempts are durable, including crashes after a claim. Timeouts, 429 and 5xx
are retried with 5, 10, 20, 40, 80, 160, then at most 300 seconds delay, up to the configured
attempt limit. A crash on the final attempt becomes BLOCKED after lease expiry.
S2 409 is REJECTED; other 4xx except 429 are BLOCKED. Token-endpoint 429 is retryable;
other token-endpoint 4xx are BLOCKED;
token-service connection/5xx failures are PENDING. Authentication failure invalidates the cached token.
No successful completion is reported without checking the S2 response.

Blocked/rejected rows do not retry automatically. Investigate the fixed error code and configuration
with dispatch/service owners. After correcting the cause and checking S2 state, an authorized database
operator may explicitly requeue one proof (never edit evidence):

```sql
UPDATE dispatch.proof_of_delivery
SET completion_state = 'PENDING', attempts = 0, next_attempt_at = now(),
    lease_token = NULL, last_error_code = NULL
WHERE id = :proof_id AND completion_state IN ('BLOCKED', 'REJECTED');
```

There is no distributed transaction or rollback of S2 completion. S2 records the service actor;
S3 records the courier actor. S2's existing outbox publishes `parcel.status.updated`; S4 uses
the existing event contract. POD evidence is never sent to either downstream service.

## Errors

Errors use existing Problem Details conventions with a stable `code`.

| Status | Examples |
|---|---|
| 400 | `INVALID_REQUEST`, `INVALID_PROOF` (includes `fieldErrors`) |
| 401 | Missing/invalid JWT, `INVALID_SUBJECT` |
| 403 | Wrong role, inactive courier, `DELIVERY_FORBIDDEN` |
| 404 | `ASSIGNMENT_NOT_FOUND`, `PROOF_NOT_FOUND` |
| 409 | `PROOF_CONFLICT` |
| 503 | `PROOF_STORAGE_UNAVAILABLE`, `COURIER_VERIFICATION_FAILED` |

S2 transition failures happen asynchronously: POST may already have returned 201/PENDING;
subsequent GET returns REJECTED, rather than retroactively changing the accepted POST to 409.
Dependency response bodies, credentials and evidence are not included in operational errors/logs.
The UI reconciles GET proof before each POST and after a failed POST; it preserves inputs on
recoverable errors, displays immutable saved evidence and polls PENDING proof every three seconds.

## Configuration

Existing S3 database and JWT environment variables remain required. Additional variables:

| Variable | Default |
|---|---|
| `IDENTITY_BASE_URL` | `http://localhost:8081` |
| `PARCEL_BASE_URL` | `http://localhost:8082` |
| `POD_TOKEN_URI` | Empty (fails closed) |
| `POD_CLIENT_ID` | Empty (fails closed) |
| `POD_CLIENT_SECRET` | Empty (fails closed) |
| `POD_WORKER_ENABLED` | `true` |
| `POD_POLL_INTERVAL_MS` | `2000` |
| `POD_MAX_ATTEMPTS` | `8`, accepted range 1–20 |

Provisioning owner must supply a confidential Keycloak client with service accounts enabled,
client-credentials grant, `SERVICE` realm role, `zentro-api` audience (or configured S2 audience),
and a securely injected secret. Use trusted HTTPS endpoints outside local development. No client,
human role or realm export was changed here. Tokens are cached with an expiry margin and never
stored in the database. Do not enable HTTP wire/SQL parameter tracing on sensitive production traffic.

## Verification and known external blockers

JUnit/MockMvc tests cover authorization, identity resolution, field normalization, client authentication,
S2 outcomes and worker recovery. PostgreSQL Testcontainers tests cover migrations, uniqueness,
concurrency, rollback, immutability, lease fencing and retry persistence. Vitest/RTL/MSW tests cover
delivery pages, forms, retrieval, errors, limits, duplicate clicks and lost-response reconciliation.

External blockers remain: evidence-field approval; Identity's duplicate V4 migrations;
`UnavailableParcelSource` preventing production assignment creation; missing confidential S3 client;
and unverified authenticated S1–S4 end-to-end operation. Tracking projection initialization is an
existing S4 dependency, unchanged by this implementation. S2 outbox publishing and S4 Kafka consumption
must both be enabled in a configured environment. Tests using mocked HTTP do not establish live integration.

## Completion-worker diagnostic context (#143)

Proof insertion captures diagnostic context in nullable internal columns owned
by S3. The leased completion worker restores that context for each attempt and
its approved REST call to S2, including after restart. No evidence, lease,
retry, authorization or API response contract changes. Legacy rows use the
proof ID as correlation and a new root trace. See
[observability](../architecture/observability.md) for migration and scope rules.
